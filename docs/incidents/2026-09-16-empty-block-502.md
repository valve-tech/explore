# The empty-block 502, and the index damage it caused

A block with no transactions could not be read through `one.valve.city`. It
stalled the Ethereum scraper for five days and, in a separate earlier failure,
left 1.94 million blocks of the mainnet index incomplete. Both are fixed. This
file is the durable record, because valve-prod's journal keeps under 8 hours and
had already rotated past this window before anyone asked.

## What a client saw

Mainnet block 25,948,788 holds zero transactions and carries the empty-trie
transactions root. Through the gateway:

| Call | Result |
|---|---|
| `eth_getBlockTransactionCountByNumber` | HTTP 502 after 9.1 s |
| `eth_getBlockReceipts` | HTTP 502 after 18.1 s |
| `trace_block` | HTTP 502 after 18.1 s |
| `eth_getBlockByNumber` (the header) | HTTP 200 in 0.1 s |
| the same three on a full block | HTTP 200 in 0.1–1.0 s |
| a public node, same empty block | `0x0` in 0.1 s |

**The body depended on batching.** A single call returned `text/plain` reading
`error code: 502`, with Cloudflare's headers and no `x-powered-by` — Cloudflare's
own page, which no JSON-RPC client can parse. The identical call inside a batch
returned HTTP 200 carrying a well-formed `-32603 "RPC proxy unavailable"`, which
is valve's relay error verbatim. So the relay answered the batch; the single-call
body was substituted.

## Who made the 502 (narrowed 2026-09-16)

Two facts, both from captured artifacts rather than from absent logs:

1. **The relay did not answer.** It runs Express and does NOT disable
   `x-powered-by` — `packages/relay/src/server.ts:23` disables only `etag`, and
   there is no helmet. Every 200 captured through the same path in the same
   window carried `x-powered-by`. The 502 did not.
2. **Caddy did not mint it.** The indexer's proxy archive holds six lines in the
   whole hour 00:50–01:50Z, and none at 00:57:30–00:58:30Z when the 502 arrived.
   Caddy provably logs the 502s it generates — 3,346 such `http.log.error`
   entries exist — so it passed this one through, which is why it is unlogged.

So Cloudflare produced that body after failing to get a response from its own
origin. But the TIMING is still the relay's, 9.1 s and 18.1 s matching its
budgets exactly. The shape that fits everything: the relay exhausts its budget,
then fails to respond at all, and Cloudflare turns that into its own page. A
relay that answered its own 502 would have carried `x-powered-by`.

Open question for the relay's owners: on the single-call path, is there a branch
where the budget expires and the handler returns without writing a response? The
batch path demonstrably writes, because its `rpcError` arrived verbatim.

Weight the evidence correctly, and know the sample size:

- The **control is solid** — several 200s through the same path in the same
  window, all carrying `x-powered-by`.
- The **absence side is n=1**. Headers were captured on exactly one 502, the
  00:57:51Z single call. Earlier probes recorded status, timing and body but not
  headers. The failure is no longer reproducible, so the sample cannot grow.
- The Caddy silence is corroboration only. An argument from a log's absence was
  wrong twice on this same night.

What keeps the conclusion standing is that the timing arithmetic is independent
of the header, and points the same way. If a source reading of the commit
production ran shows the single-call path always writes, that beats one capture.

Also worth recording: **no relay-authored 502 was ever captured.** The single
call produced Cloudflare's page; the batch produced HTTP 200 carrying the
`rpcError` object. So commit `33bb68d`, which changed these handlers from 502 to
503 with `Retry-After: 1`, may have altered a branch that never fired for single
calls and left the hang untouched. The test that matters asserts that a response
is written at all, not which status it carries.

## Why it took 9 and 18 seconds

The relay's own timeout budgets, not the node's work. `isSlowMethod` counts
`eth_getBlockReceipts` by membership and `trace_block` by its `trace_` prefix:

    not slow:  3,000 ms x 3 attempts  =  9,000 ms   (measured 9.1 s)
    slow:      9,000 ms x 2 attempts  = 18,000 ms   (measured 18.1 s)

## The underlying defect

eRPC decides a result is empty by its **shape** and exempts it by **method name**.
`util.IsBytesEmptyish` treats `null`, `[]`, `{}`, `""`, `0x` and `0x0` as empty —
verified by running it at `3ec22bf8`: `"0x0"`, `0x0` and `"0x000"` are all empty,
while `"0x1"` and `"0x2cd"` are not. The exemption is an exact-string list, so any
method that legitimately returns a zero and is not listed sweeps every upstream
before answering.

`eth_getTransactionCount` never suffered because it is on the default list, under
the comment "zero value is a real value, not absence" — upstream acknowledging the
conflation and working around it for five methods.

Proved by a controlled before/after when valve added five methods to the list:

| Call | Before | After |
|---|---|---|
| uncle count on a **full** block | 645 ms | 97 ms |
| tx count, empty block | 608 ms | 100 ms |
| block receipts, empty block | 611 ms | 88 ms |
| receipt by unknown hash *(not added)* | 644 ms | 635 ms |
| `trace_block`, empty block | 609 ms | 634 ms |

`trace_block` is unchanged because it sits on `markEmptyAsErrorMethods`, which
converts the empty to an error before anything reads the accept list.

## What actually ended the 502

An eRPC **restart** on each edge — 01:33:47Z and 01:36:14Z — running the old
binary and the old config. Not the binary roll at 01:41–01:44Z, and not a config
change. Chain-1 calls over 8 s were logging `successfully forwarded` at
8998–9012 ms and stopped dead at each box's restart. So the cause was accumulated
state, and a wedge that returns will not be fixed by the new binary.

## What we run because of it

`valve-empty-block-shim` (`/valve/docker/empty-block-shim.py`, a compose service)
sits between `scraper-eth` and `rpc-proxy`. It answers the three methods itself
ONLY when the block header proves the block empty, and it refuses an empty trace
for a block that has transactions — the 2026-04 failure that damaged the index.
Keep it until eRPC's `traceBlockGasReconciliation` is **observed** working on
chain 1, not assumed.

## Probes

`valve-tech/probes/` — `empty-block-502.py`, `empty-result-latency.py`,
