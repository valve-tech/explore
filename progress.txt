### 2026-08-24 A 4BYTE NAME NOW ADMITS WHEN IT IS A GUESS

**The scale, measured against production today.** 4byte.directory holds every
signature anyone ever registered, so one selector usually carries several. Of
the transactions that resolve to a name at all: **77% on chain 1** (3,348 of
4,351 over 40 blocks) and **47% on chain 369** (218 of 463 over 60 blocks)
have MORE THAN ONE candidate. We printed the first one as fact. Real names we
were serving: `ijekfhacdgb` for `0x00000012` on chain 1, `rz_16jun22_88961909`
and `razor_balance` on 369 — gas-token-era names, brute-forced so the selector
had leading zero bytes.

**`UNRESOLVABLE_SELECTORS` is the wrong tool for these.** Those selectors are
real and their names are legitimately registered. The set still holds only
`0x00000000`. Do not grow it to paper over a multi-candidate selector.

`summarizeMatches` / `lookupSelectorSummaries` in `services/signatures.ts`
return the first candidate plus `candidateCount`. That count is the ONLY thing
added to the wire — one integer per row, on `RecentTx.methodCandidates` and
`AddressTransaction.functionCandidates`. The alternatives are fetched per
selector from `/api/signatures/:selector`, and only when a reader hovers:
`Tooltip` mounts its `label` lazily, so the query inside it does not exist
until the bubble opens.

**At 77% the marker cannot shout.** A loud badge on three rows in four is
noise a reader learns to skip, and then it flags nothing. `MethodName` keeps
the name and adds a dotted underline plus a footnote-sized count. Verified in
the browser at 1280 and 375; no horizontal overflow at 375.

**Guard the missing count, not the low one.** `MethodName` tests `> 1`, never
`<= 1`. TanStack Query persists responses to IndexedDB with
`staleTime: Infinity`, so a browser hands the component rows with NO count at
all — and `undefined <= 1` is false, which would have marked every stale row
as a guess of `undefined` candidates. Seen live before the guard went in.

## 2026-08-24 RECENTS NAME THEIR CHAIN

`RecentEntity` now carries the chain the entry was seen on, and the recents
rail and the ⌘K palette both build their links through one function,
`recentEntityView.hrefFor`. The palette used to call `scanPath` itself; it
does not any more, so the two surfaces cannot drift.

Which kinds get a chain is a rule, not an oversight. A transaction, a contract
and a block name theirs. An **address stays bare**, because `/address/0x…`
with no prefix is the documented "every chain" route and an address is valid
on all of them.

**The legacy decision.** An entry written before this change has no chain and
there is no way to recover one. It stays unset and links bare — exactly what
shipped before — so a resolve+redirect still finds the right chain on click.
A stored `chainId` that is not a positive integer (`null`, `"369"`, NaN) is
STRIPPED at load, because keeping one would build `/eip155/NaN/tx/0x…`. Both
paths are pinned by tests in `recentEntities.test.ts`.

The chain is deliberately NOT part of the entry's identity (`idOf`). One
address is one row whichever chain you reached it from; a revisit on another
chain overwrites the field, so the link follows the newest visit.

### HARD-WON — DO NOT RE-DERIVE

- **A bare `catch { return [] }` told readers that WPLS has no history.**
  `listAppearances` swallowed every chifra failure into an empty array, so a
  30-second timeout was served to the browser as `{transactions: [], total: 0}`
  — a 200. The address page then printed "No transactions found" about one of
  the busiest contracts on chain 369. Measured: 30.2s, the chifra cap exactly.
  The signal to tell the two apart was already being computed one line above:
  `countAppearances` returns `null` ONLY on an outage, and a genuinely empty
  address reports a real `0`. `getMergedActivity` already knew this and made
  its own second call to work around it. `getAddressTransactions` now throws a
  503 on `isAppearanceOutage()`, so every caller gets the truth and the
  workaround is deleted. **An empty result is a claim about the world — make
  sure you can prove it before you serve it.**

- **A stale route interception outlives the page that installed it.** After
  testing the home page's outage state by forcing `**/api/**` to 500, that
  route stayed armed in the browser context. The next session opened
  PRODUCTION and saw "not updating - showing data 33m old" plus "Gas oracle
  unavailable" and nearly filed a deploy regression. The tell: `/health`
  came back with a `cf-ray` and `server: cloudflare`, while every `/api/*`
  reply had NO server header, no `cf-ray`, and a 2-byte `{}` body. A reply
  that never touched the network does not carry the edge's headers — check
  for them before believing an outage.
- **A Vite HMR reconnect resets React state and looks like a bug.** The
  address page's progress counter ran BACKWARD, 1/3 -> 0/3 -> 1/3, about
  five seconds after load. It correlates exactly with a second
  `[vite] connecting... connected` in the console: the HMR socket dropped,
  forced a reload, and remounted the tree. There is no HMR client in a
  production bundle. Before chasing a reset like this, log the `[vite]`
  console lines and check the timestamps line up.
- **`vite preview` is NOT a way to verify an API-backed page.** `server.proxy`
  is dev-only; preview needs its own `preview.proxy`. Without it every
  `/api` call 404s and every section fails, so the page you are inspecting
  is lying to you for a reason that has nothing to do with your change.

- **A "state" object from a package is not a wire format.** Check for a
  `toPublishable` before serializing one wholesale. Ours lived in the relay
  and was never called; nobody noticed for as long as the endpoint existed,
  because no client read the extra fields — they were just sent.
- **`truncate` is `white-space: nowrap` + `overflow: hidden`.** A `break-all`
  flex child inside it cannot wrap, collapses to nothing, and SPILLS its text
  across whatever is beside it. This produced two separate bugs in one hour: a
  method name overlapping the fee readout, and a 66-char hash running 196px
  past the content pane. One line holds one thing.
- **A grid item defaults to `min-width: auto`** and refuses to shrink below
  its content, so `break-all` on a child never fires. `min-w-0` on the item is
  what lets it act.
- **`viewport.spec.ts` was blind for its whole life.** It asserted only
  `document.documentElement.scrollWidth <= 375`, and `app-content` is a
  `flex-1 overflow-auto min-w-0` containment boundary that absorbs overflow
  internally — the document never moves off 375. Four of nineteen routes were
  overflowing while it passed: `/ui` 223px, `/network-health` 205px,
  `/explorer` 202px, `/` 37px. It asserts the pane now, all four are fixed,
  and `KNOWN_FAILING` is empty. Keep it empty.
- **An absolutely-positioned popover still grows its scroll container.**
  `InfoTip` on `/network-health` was `absolute left-0 w-72` inside its ⓘ
  trigger; a trigger near the right edge threw all 288px of bubble past the
  pane — the whole 205px. `visibility: hidden` does not help, because a hidden
  box is still laid out. It renders through a portal at `position: fixed` now,
  clamped on screen, the same trick `primitives/Tooltip` already used. Any
  hover panel measured by that gate needs the portal.
- **An `<input>` carries a browser intrinsic width (~173px)**, and a flex item
  defaults to `min-width: auto`, so a `flex-1` box holding one will not shrink.
  That was Landing's whole 37px: the search box held its ground and pushed the
  Go button off a 375px screen. `min-w-0` on the box AND on the input.
