### Internal transactions render as a call tree

The section was five columns — Type, From, To, Value, Gas — that never said
what was being called. Four collapse into one expression per row:

```
CALL         WPLS.approve(0x98bf…cc02, 3,691,074,…) → true    24,399 gas
CALL         0x98bf…cc02.swapExactTokensForTokens(…, +3)     101,362 gas
├─STATICCALL 0x3474…c9ad.getReserves() → 445,033,858,563, …    2,504 gas
└─CALL       0x3474…c9ad.swap(1,776,662,498, 0, +2)           77,039 gas
```

**The tree was always in the trace; the wire shape threw it away.**
`flattenInternalCalls` walked a `CallFrame` tree and emitted a flat list. Each
row now carries the `depth` it sat at. Depth-first order plus a depth is
lossless — a row's parent is the nearest earlier row with a smaller depth — and
the list stays flat, so no existing consumer broke.

**Never infer the nesting from `from` chaining.** A DELEGATECALL keeps the
caller's address, so parent and child report the same `from`.

**A return type is not derivable from 4byte.** It stores argument types only.
`decodeReturn` uses a small table of signatures a standard fixes (ERC-20/721,
the V2 pair) and renders nothing for anything else. `transfer(...) => true` is
a fact; a guess would not be.

**Measured in the browser, not just in tests.** 21 calls, three depths, both
swap subtrees drawing identical guides. The first pass drew a guide at depth 1,
where a direct call renders no connector — two depth-3 rows then looked
differently indented, and only `getBoundingClientRect` on the guide spans
showed it. At 375px the tree scrolls in its own box; the page body does not.

**IndexedDB served the pre-change response** and the first render showed raw
selectors with no names. The API was already correct. Clear `keyval-store`
before believing a stale-looking page.

## 2026-08-27 I CAUSED AN OUTAGE, AND FOUND FOUR REAL BUGS FIXING IT

**Everything is back up.** All four chains answer, the otter pages render, and
the address page that started this returns rows.

```
                         before              after
all four chains          401                 200
otter address page       blank               25 rows
Ethereum address page    total 2, rows 0     total 2, rows 2
```

### The outage was mine

I ran `explore-deploy` off the `thatis-monitor-key` branch without reading what
its config change did. That branch had rotated `otterBackendKey` to an `op://`
ref, so `explorer-write-trace-env` composed the RPC URL from the **v2** key and
wrote it to the explorer box — before the api had seeded it. The commit message
predicted this failure in so many words, and the runbook's status line said
"changed in-repo and NOT deployed".

**Never run a deploy off a branch without reading the diff of its deploy
config.** `sync-code` rsyncs the WORKING TREE, not the index, so uncommitted
work deploys too — mine and anyone else's.

### Four bugs found while recovering

1. **`sync-code` shipped 789 MB of gitignored build output** to three hosts
   every deploy (`services/substreams-reference/target` 414 MB,
   `…/erc20-balance-changes/vendor` 375 MB). It blew the 600s timeout and
   failed the recovery deploy. rsync walks the tree, not the index.
2. **chifra logs lack four JSON-RPC fields** (`blockHash`, `blockNumber`,
   `transactionHash`, `transactionIndex`), so ethers rejected the receipt and
   ONE token transfer blanked a whole otter page. The `to: "0x0"` bug one field
   along.
3. **The test asserted the buggy pass-through.** It checked `logs` came back
   byte-identical to the input, so it pinned the defect rather than catching
   it. A test can encode a bug.
4. **The trace deploy plan had no relay preflight.** The otterscan plan has one
   and it works; the trace plan consumes the same key and had nothing. That gap
   is what let me take production down.

### Retiring a system key is not what it looks like

Removing an entry from `SYSTEM_KEYS` does NOT retire the key — it PROMOTES it.
`SYSTEM_KEY_IDS` is derived from the roster, and `008_key_config_rehydrate`
uses it as a skip set; drop the entry and the surviving `project_key` row stops
being skipped, so 008 republishes it to Redis as an ordinary key. It keeps
authenticating while the source says it is gone. Clearing Redis by hand is
undone by the next deploy. The fix is `unlinkedAt` on the row. Runbook
corrected (monorepo `dff0225`).

Found only because the api suite runs against a PERSISTENT local Postgres —
a fresh-DB suite goes green and proves nothing.

### Verification lessons, all of them mine today

  200 and a byte count. It is an SPA: every path returns 200 + index.html. I
  had the counter-example in the same session and used it as proof anyway.
- **The app is a HASH router.** `/auth/cli` renders the landing page;
  `/#/auth/cli` renders the route. I had a memory saying exactly this and did
  not apply it.
- **Do not verify a fix with data you just created.** My own diagnostic
  `chifra list` created the monitor for the reported address, so the sidecar

- **`explore-rollback` recreates from the CURRENT image.** After rolling back,
  `/health` still reported the new SHA. Check `version.shortSha`, not the plan
  name.
- **Piping deploy output through `sed`/`tail` buffers it.** Two runs looked

## 2026-08-27 THE RPC KEY IS DEAD, AND IT WAS LEAKING TO THE PUBLIC

Two production problems, one of them a security incident. Both found chasing
a user report that Ethereum addresses "do not load anything even though the
count is 1".

### The key leaked in every error body (FIXED, needs rotation)

Our RPC keys live in the URL **path**, and viem puts the full request URL in
the message of every transport error. `respond.fail` passed that message
straight to the client, so any failing endpoint handed a 35-character `vk_`
key to any unauthenticated caller, on all four chains:

```
{"ok":false,"error":"HTTP request failed.\n\nStatus: 401\nURL: https://one.valve.city/rpc/vk_…/evm/1
```

`scrubInternal` only stripped viem's version footer, and the `ApiError` path
was not scrubbed at all. `lib/redact.ts` now runs at the boundary — ApiError,
the 500 path, and `console.error`, because a key in a log is still a leak. It
strips `vk_` tokens, bearer tokens and URL userinfo, then collapses any
absolute URL's path, which catches key shapes we have not named. Host, status
and reason survive so the message stays diagnosable. Verified live on all four
chains: `https://one.valve.city/***`.

**The key still needs rotating.** The fix stops the bleeding; it does not undo
the exposure.

### Every chain's RPC is 401 (NEEDS THE USER)

The same key is revoked or expired: `Invalid or inactive API key` on all four
chains, `/health` reports every chain `degraded` with `blocks=0`.

The gateway is FINE — the public `vk_demo` key returns current blocks on
`evm/1` (0x18a66af) and `evm/369` (0x1a1fe06). So this is our credential, not
the service.

That is the root cause of both user reports. On Explore, chifra supplies the
appearance COUNT (so the page says "2") while every RPC hydration call 401s
and is swallowed by `catch { return null }` — count without rows. On
Otterscan, the same dead RPC sits behind it, and the ethers
`check failed (argument="to", value="0x0")` is otterscan choking on a failed
receipt.

### I shipped a regression, and it was the session's own bug class

The appearance sidecar reports honestly whether it read the whole range —
`coverage.complete` and `totalIsExact` — because it does not parse the binary
finalized chunks. **The client ignored both fields.**

An address chifra has never been asked about has NO monitor, so the unread
range is the entire chain and the sidecar returns an empty list. The address
page rendered that as "no transactions". Mainnet holds 28 monitors, so nearly
every address on the chain read as empty. Binance 14 was worse in kind: a
plausible-looking `total: 50,291,073` that had not read the gap either.

`isCompleteAnswer` now gates both call sites — use the sidecar only when it
says it read the whole range, otherwise fall through to chifra, which reads
the chunks and is already bounded by `heavyGuard`. WPLS still reports
`complete: true`, so the fast path survives.

The lesson is the one this whole session has been about, and I still walked
into it: **a fast wrong answer is worse than a slow right one**, and a source
that tells you it is incomplete has to be believed.

### Traps

- **Do not verify a fix with an address you just queried.** My own diagnostic
  `chifra list` CREATED the monitor for the reported address, so the sidecar
  then answered correctly and the bug looked fixed. It was not. Test with an
  address you have never touched.
- **`explore-rollback` recreates the container from the CURRENT image.** After
  rolling back, `/health` still reported the new SHA — the code did not
  revert. Check `version.shortSha` rather than trusting the plan's name.
- The hook at `~/.claude/hooks/no-secret-to-terminal.py` blocks `op item get`
  pipelines. It is right to; use the key rather than printing it.


## 2026-08-26 THE HEAVY ADDRESS IS FIXED. WPLS ANSWERS IN 0.5s.

**Shipped and live.** The address page that returned HTTP 524 at 125s now
answers from production in under a second, with data current to the head
block.

```
                    before                  after
WPLS page 1         HTTP 524 at ~125s       0.54 - 0.87 s
WPLS deep page      impossible              1.66 s  (page 5,000)
WPLS total          never returned          224,844,066
newest row          stale or absent         head block
small address       1.5 s                   byte-for-byte identical
```

Three pieces, all deployed:

**1. A memory cap on the chifra daemon** (monorepo `9c7dd0c`). `mem_limit:
16g` + `memswap_limit: 16g` on `valve-trueblocks`. Chosen from the monitor
size distribution at 28x: it refuses exactly WPLS (~47 GB) and USDC (~39 GB),
the two the sidecar serves, and permits every other monitor — there is a real
cliff after those two. The kernel oom-killer picks its own victim, so an
unbounded chifra threatened reth and everything else; now the cgroup kills
chifra alone and docker restarts it.

**2. The appearance sidecar** (monorepo `2d699ac`, `5a3b1c8`). A
dependency-free ESM service on `node:22-alpine`, source bind-mounted, data
volume mounted READ-ONLY, capped at 1g, published on 127.0.0.1:8090 and
routed at `chifra.valve.city/appearances`. 69 tests, green in the container.

**3. The API prefers it** (`bda900f`). `fetchAppearances` returns `null` —
never an empty list — on any failure, so an unreachable sidecar degrades to
exactly the old chifra behaviour. A body with even ONE unreadable row is also
null, because a short page would silently lose a transaction.

### What made it possible

Not speed work. The index was never slow — chifra's read path was. Raw `dd`
reads the 1.7 GB WPLS monitor in 0.70s cold; chifra takes 44-69s for the same
bytes, 63-250x slower, because it loads the whole monitor to answer anything.

And the freshness came free. The scrapers write one TSV per block under
`unchained/<chain>/unripe/`, so the newest ~1,900 blocks are a millisecond
grep. A monitor is only a derived cache. That is why the sidecar can be both
instant AND current to the block, which chifra could not be at any size.

### The gap, and why every response admits it

Finalized chunks are binary and the sidecar does not parse them, so a monitor
lagging the finalized frontier leaves a range readable by nothing here.
Measured across the live monitors it runs from -1,100 blocks (the monitor is
AHEAD, so the tiers overlap it) to **539,948 blocks — about 62 days**.

Every response carries `coverage.gap` and `totalIsExact`, and `total` is a
stated lower bound when a gap exists. Verified live: the 62-day-stale monitor
returns `totalIsExact: false` with the gap named, while still serving
head-current rows.

The two sources are reconciled by BLOCK NUMBER, not deduplication. A monitor
consolidated through block L holds everything at or below L, so tier rows at
or below L are dropped and what remains above L is exactly what the monitor
lacks. Exact, and it keeps paging as plain arithmetic.

### Traps worth keeping

- **`chifra chunks index --belongs` is not a gap-closer.** It returns an
  EMPTY result for a known-positive control (WPLS in a chunk it certainly
  appears in). Without that control I would have recorded "the gap is empty".
  Re-run the control before trusting it again.
- **A client timeout does not cancel chifra's work.** A killed request kept
  writing for hours. Our 30s abort stops us waiting, not the box working, so
  retries stack instead of replacing each other.
- **The API envelope is `{ok, result: {transactions}}`.** Parsing it as
  `{transactions}` yields a confident "0 rows" against a perfectly healthy
  endpoint. Cost me a false alarm here, and the same shape mistake earlier.
- Deep paging is a seek: offset 5,000,000 costs 0.175s on the box.

### Open

Parsing the finalized chunk format would close the gap for good. Until then
khedra's monitor service (`enabled: false`, "no watchlist yet") is the warmer
that keeps gaps near zero — but note it can no longer freshen WPLS or USDC
through chifra, because the 16g cap refuses them by design.


## 2026-08-26 THE INDEX IS PER-BLOCK CURRENT. CHIFRA'S READ PATH IS THE BUG.

**Measured directly on the indexer box (95.217.41.159:2222), read-only.**
This overturns the 2026-08-25 conclusion below it. That entry is right about
where the time goes and wrong about why.

**Chifra is 63-250x slower than the disk on the same bytes.** The WPLS
monitor is 1,798,357,424 bytes. Raw `dd`: **0.70s cold, 0.20s warm**
(2,449 / 8,736 MB/s). Through chifra: **44-69s** (~37 MB/s). So the 37 MB/s
was never I/O. It is chifra's per-record loop over 224.7M records. The data
was never the problem.

Three consecutive WPLS reads cost 69s / 55s / 54s with the file barely
growing. With nothing to freshen it still cost 54s, so **that cost is the
return path, not the freshen** — chifra hands back 224.7M appearances to
give you 25.

**`--count` is worse than a full list.** `chifra list --count` on WPLS ran
300s and was killed by the client timeout, returning nothing. The count is
`(filesize - 8) / 8`; `stat` answers it instantly.

**`firstBlock`/`lastBlock` do not bound the work.** They filter output. A
100-block window on WPLS does not return quickly, while the same window on a
small monitor takes ~1s. Same finding as `maxRecords`.

### The file format, confirmed

`.mon.bin` is a flat array: 8-byte header, then 8-byte records
(`blockNumber` uint32, `transactionIndex` uint32, little-endian), ascending.
`(1798357424 - 8) / 8 = 224,794,677`, exactly the appearance count. A
seek-read of the count plus the last 25 records takes **0.027s**.

### Four tiers, and the monitor is only a cache

The index is NOT the monitor. TrueBlocks keeps four tiers under
`unchained/<chain>/`, and coverage is contiguous:

| tier | covers | behind head |
|---|---|---|
| `finalized/` | -> 27,382,782 | ~1,090 blocks |
| `staging/` (one 23MB TSV) | 27,382,783 - 27,383,843 | ~28 blocks |
| `unripe/` (one TSV per block) | 27,383,844 - 27,383,871 | **0** |

Both TSV tiers are plain `address<TAB>block<TAB>txIndex`. The scrapers write
`unripe/` **every block**. Grepping all 28 unripe files for WPLS: **0.002s**.
Grepping the whole staging tier (14,940 hits): **0.012s**.

So per-block accuracy needs no monitor refresh at all. It is a 14ms grep of
text files that are already on disk. `monitors/*.mon.bin` is a derived cache
on top of these tiers, nothing more.

**Monitors do not advance on their own** — only a `chifra list` call
consolidates one. That fact stands. The conclusion drawn from it on
2026-08-25 (that a seek read would serve stale data) does not: the freshness
lives in the TSV tiers, not the monitor. Right now the WPLS monitor's last
record is block 27,381,192 against head 27,383,871 — **2,679 blocks, roughly
seven to eight hours stale** — because nothing has called it since the last
test.

### Reading a heavy monitor OOMs the daemon. This is reachable from production.

At 13:51:09 the kernel OOM-killed `chifra daemon` on the indexer:

```
Out of memory: Killed process 2915960 (chifra)
total-vm:95984264kB, anon-rss:52972520kB
```

**50.5 GB resident, 96 GB virtual, on a 62 GB box.** I triggered it with a
handful of concurrent WPLS probes. Docker restarted the container 15s later
and it came back healthy; the four scraper containers, the index and every
other monitor were untouched, and the index never stopped advancing.

This is not just my accident. `RestartCount` is 4, and the container had
already restarted ~9h before I touched it while its siblings sat at 2 days.
The mechanism is reachable from the product: **a user loading a heavy address
page can OOM the indexer's daemon**, and because a client timeout does not
cancel the work (below), retries stack instead of replacing each other.

Order of magnitude: WPLS is 224.7M appearances in a 1.8 GB file, and chifra
needed ~50 GB of RAM to read it. That is ~28x the file size.

The killed process left a 1.8 GB `monitors/staging/` file behind. It was
record-aligned but written by a dead process, and the next freshen would have
consolidated it into a 224M-record monitor, so it is moved aside as
`…mon.bin.orphaned-oom-20260826` rather than trusted. Staging is regenerable
from the index; the other 72 monitors were untouched.

### A client timeout does not cancel chifra's work

A killed `--count` request left `chifra daemon` (pid 2915960) writing
`monitors/staging/0xa1077a…mon.bin` for hours afterwards, past 1.4 GB and
still growing, holding the fd open. **Our 30s API timeout does not stop the
daemon**; it only stops us waiting. This is a live source of load on the box
and it is worth handling before adding any warmer that can queue more of it.

### khedra already has the warmer, switched off

`/valve/docker/khedra.yaml`: `services.monitor.enabled: false`, commented
"no watchlist yet. Disable until we have a list of addresses to track."
`sleep: 12`, `batchSize: 500`. Its control API on :8338 reports both
`scraper` and `monitor` as `paused`. Scraping is done instead by four
per-chain scraper containers. So task #34 is a watchlist plus a config flag,
not new software — but note that one WPLS freshen is expensive enough to
need thought before it goes in a 12-second loop.

### What the read path should be

Newest-first, which is what the address page shows first:

1. **`unripe` + `staging` grep** — last ~1,090 blocks, ~14ms, current to the
   block. Serves the first page of almost any address.
2. **monitor seek** — deeper pages, ~27ms, no scan.
3. **`finalized` chunk reads** — only when the monitor has fallen behind.

The warmer's job is therefore NOT freshness. Freshness is free from tier 1.
The warmer exists to keep the monitor caught up to the finalized frontier so
tier 3 stays empty and we never have to decode bloom-filtered chunks
ourselves. That gap is currently 1,590 blocks and grows without bound.

Tiers 1 and 2 can overlap after a warm, so the merge needs deduplication —
pin it with a test rather than assuming the ranges stay disjoint.

Box facts: 12 cores, 62 GB RAM, load ~8.5, 49G disk at 39%. Monitor volume:
pulsechain 73 monitors / 5.1G, mainnet 28 / 3.3G, pulsechain-v4 25 / 81M,
sepolia 2 / 92K. Volume `valve_tb_data` -> `/var/lib/docker/volumes/valve_tb_data/_data`.
No `/usr/bin/time`, no `bc` on the box. `chifra monitors` has no `--freshen`
in this build.


## 2026-08-25 A HEAVY ADDRESS: WHERE THE 30 SECONDS ACTUALLY GO

**Hydration is not the bottleneck. The appearance index is all of it.**
Measured against the live API and chifra.valve.city, chain 369.

Hydration, isolated by hitting the same page twice inside the 30s appearance
cache (so the second call is pure RPC): **25 rows in 0.96s, 100 rows in
2.58s** — about **25 ms per row**, batched and bounded. It never needed
fixing.

The index read is the whole cost. First read of the day, `list --reversed
--max_records 25`:

```
        52 appearances      1.8s      5.3M appearances     2.7s
    92,572 appearances      1.7s     30.6M appearances   125.5s -> 524
   526,139 appearances      1.9s     43.7M appearances   125.2s -> 524
                                    224.7M appearances   125.6s -> 524  (WPLS)
```

**Size is a proxy. The real driver is the FRESHEN BACKLOG.** `chifra list`
brings the address's monitor file up to head before it pages it, and that
catch-up is the bill. Two addresses of the same size prove it: 0x95b303…
(23.9M appearances) needed four attempts, while 0x28c6c0… (22.55M) answered
cold in 10.8s. The direct measurement: on 0x0cfd4b… the monitor grew
38,204,576 -> 42,286,848 bytes (~510k new appearances) during a 26.5s call,
and the very next read took 2.7s. Big monitors correlate with big backlogs
only because a busy address accrues more appearances per block.

**Four facts worth never re-deriving:**

1. **`chifra list --count` is NOT the cheap half**, whatever the old comment
   in `appearances.ts` said. It freshens the same monitor and costs the same
   order — 524 at ~125s on every monitor above 30M appearances.
2. **`firstRecord`/`maxRecords` are already used and do not rescue a big
   address.** chifra freshens before it pages, and the OpenAPI says
   `firstBlock`/`lastBlock` are "ignored when freshening". A block-bounded
   read of WPLS measured 125.5s — identical to the unbounded one.
3. **chifra.valve.city sits behind Cloudflare, which cuts the origin at
   ~100s (HTTP 524 at 125s).** Our 30s cap is not the binding limit. No
   caller can wait longer, however patient.
4. **The work is cumulative and it warms.** The first read pays; later ones
   are cheap. On a 23.9M-appearance monitor, four attempts capped at 30s
   each: `30s, 30s, 30s, then 200 in 9.2s`. On 30.6M: `524 at 125s`, then
   33.8s, then 7.3s. The index becomes answerable — nobody was ever letting
   it finish.

### SHIPPED — the background warm

`services/chifra/warmIndex.ts`. When a request-bound index read TIMES OUT, we
start the same read again with a 120s budget, outside the request, and drop
the result. The reader gets the 503 and a Retry; the retry lands on a warm
index.

**Where it earns its place, measured.** Below about 16M appearances the warm
changes nothing: one abandoned 30s attempt already warms the index, and old
and new code both answer on the second call (8.2s and 9.2s, two untouched
~15.5M monitors, same one-call/150s/one-call timeline). Higher up, one slice
is not enough — a 23.9M monitor read under 30s-only slices went
`30s, 30s, 30s, then 200 in 9.2s`. That is four page loads, and nothing in
the product told the reader to keep trying. The warm does that work in one
background pass.

Restraint is the whole design: one warm per (chain, address), at most 2 at
once, a 5-minute cooldown after each. Chain-scoped like every other cache
here.

**Only a timeout earns a warm** (`isIndexTimeout`). If chifra cannot be
reached, a longer read fails the same way, so we neither spend the daemon's
time nor promise a retry that cannot work. Proved both ways: a dead chifra
returns the plain 503 in **8.7ms**; one that accepts and hangs returns the
warming 503 at **30.0s**.

**And the promise expires.** After `HOPELESS_AFTER_FAILURES` failed warms on
one address the 503 drops the "try again" sentence. Telling a reader to retry
something that cannot work is the same lie as "no transactions found".

### STILL BROKEN — WPLS needs infrastructure we do not have

**224.7M appearances, a 1.797 GB monitor file.** It did not converge in three
consecutive ~125s reads, and its monitor file was byte-identical before and
after (1,797,444,160 bytes). The 71.6M monitor did not converge either
(524, 524, then 502 at 104s). The warm helps up to about 44M appearances and
no further.

The fix for those is on the chifra box, not in this repo: **keep the hot
monitors freshened out of band** (a scheduled `chifra list --silent` per
heavy address), and/or serve chifra from an origin without a ~100s edge
timeout. Once warm, the same reads take 2.7-10.4s — comfortably inside the
page's 40s deadline. Do NOT try to buy this back by raising

### 2026-08-25 THREE MORE EMPTY-MEANS-BROKEN SITES, AND THE TRIAGE OF THE REST

The chifra fix has siblings. I audited all 30 `catch` blocks in
`packages/api/src` that swallow a failure into `[]`, `null` or `{}` and
asked one question of each: can this empty reach a reader as a fact about
the chain? Four could. The other 26 are best-effort enrichment where
"absent" is the honest answer, and they are unchanged.

**The four, all fixed the same way — find the second signal, extract a pure
exported predicate, tell the truth on the wire, test the distinguishing
case:**

- **`getInternalTransactions`** returned `[]` for a dead tracer, and the
  route piled `.catch(() => [])` and a 10s `[]` timeout on top. The tx page
  hides an empty section, so the reader concludes there were none. **A chain
  whose RPC has no `debug_*` namespace hits this on EVERY transaction** —
  which is most of them, since `DEBUG_RPC_URL` is chain 369 only. The signal
  is the trace root: `traceTransaction` never throws, it answers `trace:
  null` on total failure, and a plain value transfer traces fine and
  flattens to `[]`. `isTraceUnavailable()`.
- **`getTokenTransfers`** had the same shape. Its receipt read throws both
  for a pending hash (honest) and for a node that never answered. viem
  separates them: `TransactionReceiptNotFoundError` means the node replied
  with a null receipt. `isReceiptMissing()`.
- **`parseSlitherOutput`** turned unreadable output into `[]`, and
  `analyzeContract` published `detectorCount: 0, error: null`. **That is a
  clean bill of health for a contract nobody analysed.** Three signals from
  Slither itself: no `{`, JSON that will not parse, and an envelope whose
  own `success`/`error` say the run failed. A clean contract emits
  `results.detectors: []`, so a real empty survives.
  `isFailedSlitherRun()`.
- **`getPrestateTrace`** returned `{}`, so `collectStateDiff` used each
  post-state as its own pre-state and the simulator printed "No state
  changes detected." **A simulated transaction always spends gas**, so an
  empty prestate map is impossible from a working tracer — that
  impossibility is the whole signal. `isPrestateUnavailable()`.

**The wire now carries the distinction, and the UI reads it.** Three new
optional flags — `internalTransactionsAvailable`, `tokenTransfersAvailable`,
`stateDiffAvailable`. Optional is deliberate: TanStack Query persists to
IndexedDB, and a response cached before these existed must not paint a
phantom failure, so an ABSENT flag counts as available.

**A hidden section is the same lie said more quietly.** `TxDetail` only
rendered these sections when non-empty. A failed section now appears, open,
saying it could not load. Hiding it lets the reader conclude there were
none — which is exactly the conclusion we were trying to stop.

**Two things I looked at and deliberately left:**

- `monitor/matchers.ts` `matchBalanceThreshold` swallows a `getBalance`
  failure into "the alert did not fire". That is a real silent failure, but
  nothing renders it, and the outer `matchAlerts` already treats a throw
  identically (log, no alert). Fixing the inner catch changes nothing
  observable. **A user's balance alert can miss a block on an RPC blip and
  nobody is told.** The fix is an alert-health channel, not a predicate.
- `ForkSimulator/ResultPanels.tsx:71` sums a null `gasEstimate` as `0n`, so
  a bundle total silently understates when one leg could not be estimated.
  Web-side, outside this sweep.

**What a green suite did not catch, again.** Every one of these four had
passing tests. The tests asserted the SHAPE of the response — an array, a
count, a diff object — and every one of those assertions is true of a lie.
The new tests each pin the case where the two empties differ, and would fail
if the predicate were inverted.

**Not browser-verified.** The four failure states are hard to provoke
locally (they need a node without `debug_*`, a broken Slither, a fork
without `prestateTracer`). The new copy is exercised by jsdom render tests,
which is not the same thing as opening the page.

### 2026-08-24 A 4BYTE NAME NOW ADMITS WHEN IT IS A GUESS

**The scale, measured against production today.** 4byte.directory holds every
signature anyone ever registered, so one selector usually carries several. Of
the transactions that resolve to a name at all: **77% on chain 1** (3,348 of
4,351 over 40 blocks) and **47% on chain 369** (218 of 463 over 60 blocks)
have MORE THAN ONE candidate. We printed the first one as fact. Real names we
were serving: `ijekfhacdgb` for `0x00000012` on chain 1, `rz_16jun22_88961909`
and `razor_balance` on 369 — gas-token-era names, brute-forced so the selector
had leading zero bytes.

**`UNRESOLVABLE_SELECTORS` is the wrong tool for these.** Those selectors are
real and their names are legitimately registered. The set still holds only
`0x00000000`. Do not grow it to paper over a multi-candidate selector.

`summarizeMatches` / `lookupSelectorSummaries` in `services/signatures.ts`
return the first candidate plus `candidateCount`. That count is the ONLY thing
added to the wire — one integer per row, on `RecentTx.methodCandidates` and
`AddressTransaction.functionCandidates`. The alternatives are fetched per
selector from `/api/signatures/:selector`, and only when a reader hovers:
`Tooltip` mounts its `label` lazily, so the query inside it does not exist
until the bubble opens.

**At 77% the marker cannot shout.** A loud badge on three rows in four is
noise a reader learns to skip, and then it flags nothing. `MethodName` keeps
the name and adds a dotted underline plus a footnote-sized count. Verified in
the browser at 1280 and 375; no horizontal overflow at 375.

**Guard the missing count, not the low one.** `MethodName` tests `> 1`, never
`<= 1`. TanStack Query persists responses to IndexedDB with
`staleTime: Infinity`, so a browser hands the component rows with NO count at
all — and `undefined <= 1` is false, which would have marked every stale row
as a guess of `undefined` candidates. Seen live before the guard went in.

## 2026-08-24 RECENTS NAME THEIR CHAIN

`RecentEntity` now carries the chain the entry was seen on, and the recents
rail and the ⌘K palette both build their links through one function,
`recentEntityView.hrefFor`. The palette used to call `scanPath` itself; it
does not any more, so the two surfaces cannot drift.

Which kinds get a chain is a rule, not an oversight. A transaction, a contract
and a block name theirs. An **address stays bare**, because `/address/0x…`
with no prefix is the documented "every chain" route and an address is valid
on all of them.

**The legacy decision.** An entry written before this change has no chain and
there is no way to recover one. It stays unset and links bare — exactly what
shipped before — so a resolve+redirect still finds the right chain on click.
A stored `chainId` that is not a positive integer (`null`, `"369"`, NaN) is
STRIPPED at load, because keeping one would build `/eip155/NaN/tx/0x…`. Both
paths are pinned by tests in `recentEntities.test.ts`.

The chain is deliberately NOT part of the entry's identity (`idOf`). One
address is one row whichever chain you reached it from; a revisit on another
chain overwrites the field, so the link follows the newest visit.
